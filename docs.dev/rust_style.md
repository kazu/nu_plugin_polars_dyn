# Rust の書き方

この fork で Rust を書くときの規約。本家 nushell の
[`devdocs/rust_style.md`(0.114.1)](https://github.com/nushell/nushell/blob/0.114.1/devdocs/rust_style.md)
を元に、この fork の方針に合わせて書き直したもの。本家と違う箇所は「本家との違い」として
明記する。設計の合意は [agreements.md](./agreements.md) にある。

## 目指すもの

読んで意味が取れ、驚きが無く、重要なところでは明示的なコード。clippy の指摘には従う。
賢い言語機能の使い方や個性は目指さない。

**本家との違い**: 本家は「まず正しく単純に書き、性能は後で」と言う。この fork は polars の
パイプラインを流す道具なので、**copy コストは最初から最小にする**。バッファは offset で持ち、
memmove は残余だけ、出力は Vec に組まずに sink へ直接書く。「小さいから許容」で余計な copy を
足さない。

## 禁止・非推奨

### nightly の言語機能

使わない。`rust-toolchain.toml` の版で通るものだけ。

### panic

ユーザ入力や外部システムの挙動で到達しうる経路で panic しない。panic はバグか、回復不能な
状態(メモリ不足など)でだけ許される。

- `.unwrap()` は禁止(`[lints.clippy] unwrap_used = "deny"`。テストでは
  `clippy.toml` の `allow-unwrap-in-tests` で許可)。
- `.expect()` や `unreachable!` を使うなら、**どの前提が破られたか**が分かる文言を付ける。
- エラーは `ShellError` / `PolarsError` で返す。

### `unsafe`

`.so` のロードと Arrow C Data Interface の受け渡しで `unsafe` が増える。書くときは
[Rustonomicon](https://doc.rust-lang.org/nomicon/intro.html) の保証を理解した上で、
すべての `unsafe` ブロックに **`// SAFETY:` コメント**を付けて、どの不変条件をどう守っているか
を書く。変更するときに何を見ればよいかがそこで分かるようにする。

- **FFI**: Rust のメモリモデルに加えて、呼び出す側の契約(所有権、`release` callback、
  version 照合、失敗時の値)を rustdoc に書く。失敗の経路をすべて回復可能にする。
- **自前のデータ構造**: `std` で表せないから `unsafe` で書く、という前に crates.io を探す。
  書くなら profiling の結果で必要性を示す。
- **チェックを外して速くする**: やらない。

### macro

**本家との違い**: 本家は `macro_rules!` を原則避ける(読みにくい、rustfmt / rust-analyzer が
中を扱えない、hygiene を外すと妙な挙動を入れやすい)。その理由は fork でも有効だが、この fork
には性能のために macro が要る場面があるので、条件付きで許す。

- generics や `#[inline]` の関数で単相化できるなら、それを先に使う。
- 型やメソッド名が違って generics で表せない分岐を**ループの外で解決**したいとき、呼び出し側の
  複製を避けるための**小さく局所的な `macro_rules!`** は可。使うときは実測で速度差が出ることを
  添える(1 要素ごとの間接呼び出しはループ不変のロードをホイストできなくする)。
- 大きい macro、crate を横断する macro、構文を発明する macro は本家と同じく避ける。

### 依存の追加

依存はコンパイル時間と監査の手間を増やす。必須で、よく使われ、保守されている crate だけ。
似た用途の crate を複数入れない。版は exact semver(`"1.2.3"`)。git 依存や path 依存は
publish する manifest には置けないので使わない(`dev/` は例外)。

## 書き方

### 深い入れ子

enum の `match` とエラー処理で右にずれていくコードは読めない。早期 `return` で不正な入力を
1 箇所で弾き、「もう検査済み」を表す型に詰め替えてから本体を書く。特別扱いを 1 つ足すために
分岐を継ぎ足さない。

### 重複

同じ規則を二度書かない。既存が再利用できない形なら、書き直すのではなく切り出してから使う。
判断は「関数が似ているか」ではなく「同じ規則を言い直しているか」。

### 抽象化

まず既存の形に引数を 1 つ足す形で書けないか試す。trait / enum / plugin に上げるのは、
それで書けないと示せてから。状態が要ると思ったら、まず純粋関数で書けないか確かめる。

### 既存コードとの差分

**消さないコードは触らない。**本家から引き継いだコードは本家との差分を最小に保ち、上流の
修正を cherry-pick できる状態にする。バグ修正に同義の書き換え(構造の平坦化、変数名変更、
イディオム置換)を混ぜない。既存関数の用途が増えても署名を変えず、一般形は新しい名前で足して
旧名を薄い層にする。

### テスト

**本家との違い**: 本家はソース内の `#[cfg(test)] mod tests` に書く。引き継いだテストはそのまま
にするが、**fork で新しく書くテストは `tests/` に置く**。`tests/` から呼べないなら、呼べるように
本体を設計し直す。

### ドキュメント

rustdoc には契約と例だけ。`# Arguments` / `# Returns` は署名の再掲なので書かない。doctest は
`no_run` にせず、フィクスチャの準備は `/// # ` の隠し行に置いて実際に走らせる。散文でコードを
指すときは関数名・型名で、行番号は書かない。ドキュメントに書いたコマンド例はその場で 1 回
実行する。
